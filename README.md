НАЗВАНИЕ КЕЙСА:
«Автоматический расчёт заказов поставщикам для пополнения склада»

КОНТЕКСТ ПРОБЛЕМЫ:
Менеджер закупа сейчас вручную рассчитывает пополнение склада в Excel. Из-за этого заказы поставщикам формируются редко, а разовые крупные продажи искажают регулярную потребность. В результате компания либо закупает лишний товар и замораживает деньги на складе, либо слишком поздно обнаруживает дефицит.

Необходимо создать сервис, который:
1. Получает историю продаж.
2. Получает текущие остатки.
3. Получает данные о товарах в пути.
4. Определяет разовые и аномальные всплески продаж.
5. Не позволяет этим всплескам необоснованно увеличивать регулярную закупку.
6. Прогнозирует нормальный спрос.
7. Определяет риск дефицита.
8. Рассчитывает, какой товар, в каком количестве и когда нужно заказать.
9. Учитывает срок поставки, минимальную партию, размер упаковки и страховой запас.
10. Объясняет каждую рекомендацию понятным языком.
11. Формирует готовые черновики заказов поставщикам.
12. Позволяет менеджеру моделировать изменения спроса, задержки поставки и ограниченный бюджет.

ВАЖНЫЙ ПРИНЦИП ПРОДУКТА:
LLM не должен самостоятельно придумывать числа и выполнять критические расчёты «на глаз».

Все количественные расчёты должны выполняться детерминированными функциями TypeScript:

- бюджетная оптимизация;
- выбор поставщика.

OpenAI-модель должна:

- формировать черновик заказа.

Числа, показанные AI, должны браться только из результатов инструментов приложения.

6. ОБНАРУЖЕНИЕ АНОМАЛИЙ
==================================================

Анализируй продажи по неделям. Если данные ежедневные, сначала агрегируй их.

Храни два ряда:
1. rawHistory — реальные продажи;
2. cleanedHistory — продажи после обработки выбросов.

Никогда не удаляй исходные точки без следа.

Для поиска выбросов используй устойчивую комбинацию:
- IQR;
- modified Z-score на основе median absolute deviation;
- сравнение с локальной медианой;
- признаки разового крупного заказа, если доступны customerId или orderId.

Примерные критерии:
- IQR threshold около 1.5–2.0;
- modified Z-score около 3.5;
- точные параметры вынеси в конфигурацию.

Учитывай ограничения:
- при маленьком количестве наблюдений не удаляй данные агрессивно;
- если история меньше 8 периодов, показывай низкую уверенность;
- сезонный пик не должен автоматически считаться ошибкой;
- промо-продажа должна быть отмечена отдельно;
- пользователь должен иметь возможность вручную включить или исключить аномалию;
- после изменения пользовательского решения анализ пересчитывается.

Для каждой аномалии покажи:
- дату;
- количество;
- обычный диапазон;
- во сколько раз значение выше нормы;
- вероятную причину;
- влияние на прогноз;
- влияние на рекомендуемый заказ;
- статус: исключена, учтена частично или оставлена.

Возможные категории:
- разовая оптовая продажа;
- промо;
- сезонный пик;
- возможная ошибка данных;
- недостаточно данных для классификации.

LLM может предложить текстовую классификацию, но решение о математическом влиянии должно приниматься детерминированным кодом.

==================================================

Не используй тяжёлую ML-инфраструктуру.

Реализуй несколько простых, объяснимых методов:

2. Weighted moving average.
3. Simple exponential smoothing.
4. Seasonal naive, только если данных достаточно и сезонность действительно определяется.

Автоматически сравни методы на небольшом holdout-периоде:
- последние 3–6 периодов;
- используй MAE и WAPE;
- выбери метод с меньшей ошибкой;
- если данных недостаточно, используй безопасный fallback.

Показывай пользователю:
- выбранный метод;
- почему он выбран;
- прогноз;
- диапазон неопределённости;
- ошибку backtest;
- уровень доверия.

Не показывай ложную точность.
Количество округляй разумно.
Не отображай прогноз вида 12.738425 штуки.

Для новых товаров:
- используй медиану категории, если категория доступна;
- иначе используй простой fallback;
- обязательно покажи предупреждение «Недостаточно истории».

8. РАСЧЁТ ПОПОЛНЕНИЯ
==================================================

Используй прозрачные формулы.

Основные переменные:

averageDemand = прогноз среднего спроса за период
demandStdDev = стандартное отклонение очищенного спроса
leadTimePeriods = leadTimeDays / длина периода
reviewPeriod = период между пересмотрами заказа
serviceLevelZ = коэффициент уровня сервиса

Примерные коэффициенты:
- 90%: 1.28
- 95%: 1.65
- 97.5%: 1.96
- 99%: 2.33

stockPosition =
onHand
+ inTransit
- reserved
- backorders

safetyStock =
serviceLevelZ
× demandStdDev
× sqrt(leadTimePeriods + reviewPeriod)

reorderPoint =
averageDemand × leadTimePeriods
+ safetyStock

targetStock =
averageDemand × (leadTimePeriods + reviewPeriod)
+ safetyStock

rawRecommendedQuantity =
max(0, targetStock - stockPosition)

После этого:
1. Учитывай MOQ.
2. Округляй вверх до packSize.
3. Не создавай отрицательное количество.
4. Если заказ не нужен, возвращай 0 и объясняй почему.
5. Если stockPosition выше reorderPoint и дефицит до следующего пересмотра не прогнозируется, заказ обычно равен 0.
6. Если поставка приезжает после прогнозируемого дефицита, отмечай срочный риск.
7. Если данных о lead time нет, используй настраиваемый fallback и показывай предупреждение.
8. Если товара в пути достаточно, не предлагай лишний заказ.
9. Если товар уже в избытке, показывай overstock warning.
10. Если нет подходящего поставщика, не выдумывай его.

Сохрани полный calculation breakdown:
- прогноз;
- lead time;
- потребность на lead time;
- страховой запас;
- остаток;
- резерв;
- товар в пути;
- MOQ;
- pack size;
- итог.

Пользователь должен видеть расчёт, а не просто магическое число.
